# docs/012-ipc.md

# IPC Engine

Version : 2.0 (Draft)

---

# 1. Objectif

L'IPC constitue la **seule API officiellement supportée** de SyFi (cf. `003-architecture.md` Partie 4, §51). Les crates Rust du Core ne sont pas considérées comme une API publique — cela permet de faire évoluer le Core sans casser les applications clientes.

Ce document précise le format concret du protocole, laissé ouvert dans `005-daemon.md`.

---

# 2. Transport

- Socket Unix local (Linux/Android) ou named pipe (Windows).
- Contrôle d'accès de premier niveau via les permissions du système de fichiers (socket lisible/inscriptible uniquement par l'utilisateur courant) ou l'ACL du named pipe.

---

# 3. Choix : protocole custom

Pas de gRPC ni de JSON-RPC générique — cohérent avec l'objectif de robustesse (efficacité + sécurité) et la volonté de réutiliser cette couche telle quelle dans les autres applications de l'écosystème.

- **Sérialisation** : CBOR, cohérent avec le choix déjà fait pour le manifest (`008-manifest.md`) — une seule bibliothèque de sérialisation dans tout le Core.
- **Framing** : messages préfixés par leur longueur (u32) sur le socket local — pas de négociation HTTP/2 ni de couche de transport superflue pour un canal purement local.
- **Schéma versionné** : chaque message porte un numéro de version de schéma, pour permettre à des applications développées à des rythmes différents de rester compatibles sans mise à jour synchronisée.

---

# 4. Sessions et capacités

Cf. `005-daemon.md` §14-16 pour le pipeline général (`Request → Session → Capability Check → Authorization → Service → Response`). Ce document précise le format du jeton.

## 4.1 Format du jeton de capacité

- **Jeton opaque aléatoire** de 32 octets — pas de structure signée à vérifier, l'IPC étant purement local, la complexité d'un JWT ou d'une structure cryptographiquement signée n'apporte rien ici.
- Généré au premier appairage entre une application cliente et le démon.
- Le démon conserve une **table de capacités locale** :

```
jeton → { nom_app, portées_accordées, date_création }
```

## 4.2 Portées (scopes)

Ensemble fixe et restreint défini à la compilation — une simple recherche dans une table, pas un langage de permissions à concevoir. Liste initiale minimale, à étendre selon les besoins réels des applications de l'écosystème :

```
contacts:read
coffres:list
coffre:contenu:<id>
sync:statut
```

## 4.3 Stockage et révocation

- Le jeton est stocké côté client dans le **stockage sécurisé natif de la plateforme** (Android Keystore, Windows Credential Manager, Secret Service/libsecret sous Linux) — jamais en fichier plat.
- Une interface "applications connectées" côté utilisateur permet de retirer une entrée de la table à tout moment ; l'application concernée perd l'accès immédiatement et doit se réappairer.
- Pas d'expiration automatique par défaut en V1 (le jeton reste valide jusqu'à révocation explicite) ; une expiration par inactivité pourra être ajoutée plus tard sans changer la structure.

---

# 5. Composants d'UI partagés

Au-delà de l'accès aux données, certaines applications de l'écosystème peuvent avoir besoin d'embarquer directement des fragments d'interface (ex. un sélecteur de contact, un explorateur de coffre partagé) plutôt que de les réimplémenter. Ces composants sont packagés séparément (Kotlin pour Android, web-component ou crate Tauri pour desktop) et consommés par les applications clientes qui le souhaitent — cette brique reste la moins mature du projet et sera précisée une fois les besoins réels des autres applications mieux connus.

---

# 6. Erreurs

```
Unauthorized
UnknownCapability
InvalidToken
SchemaVersionMismatch
SessionExpired
MalformedRequest
```

Toutes héritent de `IPCError`.

---

# 7. Invariants

- Aucune requête n'est traitée sans vérification de capacité préalable.
- Un jeton révoqué est immédiatement invalide, sans délai de grâce.
- L'IPC ne contient aucune logique métier — elle ne fait que router vers les services du démon après vérification.
- Le format du protocole est versionné indépendamment des autres formats du système (cf. `003-architecture.md` Partie 4, §45).

---

# Conclusion

L'IPC constitue la frontière de confiance entre le démon SyFi et le monde extérieur. En la construisant comme un protocole custom léger, versionné et fondé sur des capacités explicites plutôt que sur une confiance implicite, cette couche reste réutilisable telle quelle par toute future application de l'écosystème sans compromis de sécurité.
